在一个仓库里同时跑两三个 Agent，用不了十分钟就会遇到两个实际问题。

第一个是互相踩文件。一个 Agent 在改导航栏，另一个在顺手修登录接口，两个进程共享同一个工作目录时，`git status` 很快会混成一锅粥。你连某行改动到底是谁写的都分不清，更别说分别提交或回滚。

第二个是写入范围心里没底。分支虽然隔开了，可 Agent 进程还是跑在你的本机用户权限下，执行脚本、清理缓存或者误判路径时，仍然可能写到当前项目目录外面。把每个小需求都塞进 Docker 容器当然更彻底，但准备镜像、挂载依赖、同步工具链的开销，对日常改几行代码来说又太重。

Ait 在创建工作区时把目录分成三档，就是按这两种需求拆开的。

## 本地目录、普通 Worktree、沙箱 Worktree 分别管什么

在项目里新建工作区时，有三种方式：

- **本地目录**：直接用项目现有的检出目录。适合一次只做一件事，或者本来就想在当前分支上接着改。
- **新建 Worktree**：基于 Git worktree 分配一个独立目录和分支。多个 Agent 各自读写自己的目录，提交记录和未暂存改动互不干扰。
- **沙箱 Worktree**：在 Git worktree 的基础上，再给 Agent 进程加一层操作系统级的写入限制，把写入范围收紧在工作区允许的路径内。

普通 Worktree 解决的是并行开发的目录和分支冲突，它对进程权限没有任何额外约束；沙箱 Worktree 才开始限制进程能往哪里写。两者的分工很直接，不需要混为一谈。

## 沙箱 Worktree 的实际边界

在支持的 macOS 和 Linux 主机上，沙箱 Worktree 目前可用于 **Claude Code、Codex、Pi、Oh My Pi、OpenCode 和 MiniMax Code**。

有两条边界需要提前知道，免得把它当成虚拟机来用：

1. **它重点限制写入，不等于完整的读取隔离或网络隔离。** Agent 仍然要联网调用模型服务，也可能需要读取系统工具链或只读依赖。如果你的场景要求彻底隔离网络、环境变量或本机所有敏感文件，还是应该用独立虚拟机或容器。
2. **Linux 主机依赖 `bubblewrap >= 0.8.0` 和非特权用户命名空间。** 通过 `.deb`、`.rpm` 或 Arch AUR 的 `ait-bin` 安装桌面版时，包依赖会自动带上 `bubblewrap`；如果用的是 AppImage、`tar.gz` 或 `ait-git`，需要自己装好 `bubblewrap` 并确认系统允许非特权用户命名空间。

把这一层做成轻量级写入边界，而不是强制要求 Docker，原因是大多数日常开发任务只需要“别把仓库外的文件写坏”，同时还要能直接用主机上装好的 Rust、Node、Python 和本地缓存。

## 并行跑完之后怎么收尾

Worktree 创建出来后，项目初始化脚本可能还在后台跑，先确认一眼当前分支并等初始化完成再发任务，能省掉不少莫名其妙的依赖报错。

几个并行任务陆续跑完后，工作区里的 Git 流程按实际状态走就行：

- 工作区主按钮会根据当前分支和 PR 状态自动切到下一步操作，比如提交、创建 PR、推送或查看 PR。需要直接操作 GitHub / GitLab 时，工作主机上的 `gh` 或 `glab` 要先登录好。
- 升级到 v0.2.26 客户端和兼容主机后，可以在分组 Git 面板里分类查看改动，分支落后于远端时也能直接用**变基到远端**把提交整理干净。
- 合并完成后，确认这个工作区里没有还在跑的 Agent，也没有漏掉的权限审批，再从工作区菜单归档。如果中途想推倒重来，符合条件的托管 Worktree 可以用重置功能，但确认前最好看清分支和会被清空的文件。

一套流程跑顺之后，并行开三四个任务基本不用再手动 `git stash` 来回切分支。关于目录、Worktree 和 Git 操作的完整说明，可以看 [工作区文档](/zh/docs/workspaces/)，Linux 依赖细节在 [平台支持](/zh/docs/platforms/)。
