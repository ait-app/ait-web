让编程 Agent 连续干两三个小时，最常发生的不是代码写不出来，而是你自己先迷路了：刚才那段回复改的是哪个分支？终端里那次报错对应的又是哪一版修改？聊着聊着切去修另一个 Bug，回来已经想不起刚才验证到哪一步。

在 Ait 里把工作区用顺手，基本就是把这些零散信息绑回同一个地方。

## 一件事开一个工作区，名字直接写目标

在项目里新建工作区时，别起“测试”“临时”这种过两天连自己都认不出来的名字，直接用具体任务命名，比如 `fix-oauth-callback`、`mobile-nav-390px` 或 `docs-daemon-upgrade`。

在这个工作区里，Agent 对话、目录文件、终端和 Git 变更都在同一屏。切回这个工作区，你一眼就能看到它动了哪些文件、停在哪个分支，不用再在一排终端标签页里挨个 `git status`。

## 给任务时把验收方式一起写进去

相比“帮我优化一下首页导航”，下面这种描述能省掉好几轮来回拉扯：

> 调整首页导航，让它在 390px 宽的手机屏幕上能正常展开和收起。沿用现有样式，不要引入新依赖，改完运行一次构建确认没有报错。

把修改范围、不能碰的东西和验收命令一次交代清楚，Agent 少猜一半，你后面看 Diff 也知道该重点查哪几处。

## 看总结之前，先看 Diff 和运行结果

Agent 的收尾总结很容易写得很自信，但它有没有顺手改错别的文件、漏掉边界条件，只有 Diff 和构建输出说了算。

- 先扫一遍改动文件列表，确认没有意外波及无关目录；
- 在工作区终端跑项目实际的测试或构建命令；
- 涉及页面和样式改动时，直接打开预览看渲染效果，编译通过不代表布局没歪。

## 任务分叉时，别硬挤在同一个目录里

做到一半突然要插队修个线上问题，或者想同时试两种实现方案，直接开一个新的 Git worktree 工作区，让两个任务各自占独立目录和分支。想顺便限制 Agent 写入范围的话，还可以选沙箱 Worktree，具体区别看 [普通 Worktree 和沙箱 Worktree 差在哪](/zh/blog/sandboxed-worktrees/)。

## 给下一轮会话留一张交接条

一轮活干完，如果想换个 Agent 接着做，或者打算明天再回来验证，有两样现成工具可以少打很多字：

- **工作区记事本**（在测试功能中开启）：每个工作区共享一份存在主机数据目录里的 Markdown，不进 Git 提交。把“已经查过什么、还有哪个坑没填、下一步跑什么命令”随手记在里面，桌面和网页都能改，具备权限的 Agent 也能通过 Ait MCP 直接读写。
- **导出时间线**：在上下文详情里导出 Markdown 或 HTML，方便归档或者发给同事一起看。

更多关于目录模式、记事本和 Git 操作的细节，见 [工作区文档](/zh/docs/workspaces/) 和 [Agent 会话](/zh/docs/sessions/)。
