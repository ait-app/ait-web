Codex や Claude Code をリモートの Linux ホストにインストールすると、最初のサインインでたいてい同じ箇所に引っかかります。

CLI がターミナルに認可 URL を出力し、ブラウザーでログインするよう促します。認証が終わるとプロバイダーは `http://localhost:1455/...` のようなループバックアドレスへリダイレクトしますが、そのポートで待ち受けているのは CLI を動かしているリモートホスト側です。リモートマシンにはデスクトップ環境がなく、手元のノート PC のブラウザーにとって `localhost` はノート PC 自身を指してしまいます。

よくある回避策は 3 つです。SSH でコールバックポートを転送するか、`~/.codex/auth.json` をコピーして持ち運ぶか、デバイスコードや認可コードの貼り付けに切り替えるか。どれも動きますが、毎回ひと手間かかります。

すでに Ait デスクトップ版でそのホストへ接続しているなら、ワークスペース内で内蔵ブラウザーのタブを開くのが一番手っ取り早いです。内蔵ブラウザーの通信出口はワークスペースが属するホストに従うため、CLI が出した URL をそのまま貼り付ければ、ログインページもループバックコールバックもリモートホスト側に届きます。

## なぜ CLI は localhost に戻ってくるのか

これはローカル CLI 向けの標準的な OAuth ループバックリダイレクトです。サインイン中、CLI は `127.0.0.1` の一時ポートで待ち受け、ブラウザーのリダイレクトから認可コードを直接受け取ります。開発者のマシンごとに公開コールバック URL を登録せずに済み、認可コードも第三者サーバーを経由しません。

リモートホストでだけ面倒になるのは、CLI が動いているマシンのループバックへブラウザーが到達できなければならないからです。ノート PC のブラウザーで `localhost:1455` を開いても、サーバー側の Codex には届きません。

## 内蔵ブラウザーの通信経路

Ait デスクトップクライアントのブラウザータブは画面こそ手元の PC に描画されますが、通信経路は開いているワークスペースに追従します。

- **ローカルのワークスペース**：手元のマシンから直接通信します。
- **リモートのワークスペース**：アカウントリレー、TCP、または SSH で張った接続を経由し、`localhost` を含む HTTP・HTTPS・WebSocket 通信をそのホストのデーモンへ転送します。DNS 解決もホスト側で行います。

そのため、リモートワークスペース内で `localhost:1455` を開くと、リモートホストのループバックポートに接続されます。ホストがオフラインになったり接続が切れたりしても、黙って手元の PC 側へフォールバックすることはありません。誤って別のマシンへサインインを送らないための挙動です。

転送されるのは生の TCP バイト列で、URL は書き換えず HTTPS 証明書も Chromium 自身が通常どおり検証します。中間者復号は行わず、認証情報は各 Web サイトと CLI が直接扱います。

> 実装の詳細はリポジトリの [ADR-152](https://github.com/ait-app/ait/blob/main/docs/decisions/clients/adr-152-remote-workspace-browser-loopback.md) と [ADR-186](https://github.com/ait-app/ait/blob/main/docs/decisions/clients/adr-186-workspace-browser-egress.md) に記録しています。

## リモートホスト上の Codex にサインインする

1. Ait デスクトップ版で対象の作業ホストに接続し、ワークスペースを開きます。
2. ターミナルタブを開き、`codex login` を実行します。
3. ヘッドレス環境ではブラウザーの自動起動に失敗するので、ターミナルに表示された認可 URL をコピーします。
4. ワークスペースのタブバーから内蔵ブラウザータブを開き、URL を貼り付けてアクセスします。
5. ChatGPT アカウントでサインインします。完了後に `localhost:1455` へリダイレクトされ、ホスト上の Codex がコールバックを受け取ってログインが完了します。
6. ターミナルに戻って確認します。

```sh
codex login status
```

Codex の既定のコールバック先は `localhost:1455` です。公式の [Authentication ドキュメント](https://developers.openai.com/codex/auth) には、ヘッドレス環境向けのデバイス認証や SSH 転送も案内されています。お使いのバージョンが `codex login --device-auth` に対応していれば、ループバックを使わずに進めることもできます。

## リモートホスト上の Claude Code にサインインする

手順は同じです。

1. ワークスペースのターミナルで `claude auth login` を実行するか、`claude` セッション内で `/login` を実行します。
2. ターミナルに出力された認可 URL をコピーします。
3. 内蔵ブラウザータブで開き、Claude アカウントにサインインします。
4. リモートホスト側でコールバックを受信したら、ターミナルで状態を確認します。

```sh
claude auth status
```

最近の Claude Code は、ループバックに到達できない場合に OAuth コードをターミナルへ貼り付ける方法にも対応しています（公式の [2026 W18 アップデート](https://code.claude.com/docs/en/whats-new/2026-w18) を参照）。内蔵ブラウザーを使えば、そのコピペの手間を省けます。

## ログイン以外のホスト内サービスにも使える

同じ経路はリモートホスト上で動かしている開発サーバー、Storybook、Jupyter、管理画面、ホストの社内 IP からしか入れない内部サイトにもそのまま使えます。そのホストに属するワークスペースであれば、`localhost` や `127.0.0.1`、ホスト側の内部アドレスがホスト経由で名前解決・接続されます。

アドレスバーは `localhost` などのループバックには自動で `http://` を補い、それ以外のアドレスは既定で `https://` を付けます。スキームを指定したいときは完全な URL を入力してください。

## 前提条件と注意点

- **デスクトップクライアント限定**：内蔵ブラウザーは現在 Ait デスクトップ版のみに搭載されており、Web とモバイル版にはありません。
- **新しめのホスト側デーモンが必要**：リモートの `aitd` やデスクトップ同梱デーモンが古い場合は更新を促されるため、先にホスト側をアップデートしてください。
- **ホストのブラウザー用プロキシ設定は読み込まない**：通信はホストの DNS と TCP スタックを使いますが、ホスト側デスクトップブラウザーのプロキシ設定は引き継ぎません。外向き通信にプロキシが必要なホストは別途ネットワーク設定が必要です。
- **到達性はホスト側のネットワークに依存する**：OpenAI や Anthropic へ接続できるかどうか自体は、リモートホスト側の通信環境に従います。
- **リモートホストごとに独立したプロファイルを保持する**：Web サイトのログイン状態は保持され、ブラウザーデータを消去すると一緒にクリアされます。

リモートホストの構築から進める場合は [スタンドアロンデーモン](/ja/docs/daemon/) を、各エージェントの導入と認証については [エージェントのセットアップ](/ja/docs/providers/) をご覧ください。
