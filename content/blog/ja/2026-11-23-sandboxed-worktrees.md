1 つのリポジトリでコーディングエージェントを 2〜3 本同時に走らせると、10 分もしないうちに 2 つの現実的な問題にぶつかります。

1 つ目は、お互いのファイルを踏み合うことです。片方がナビゲーションを直している裏で、もう片方がログイン処理をいじっていると、同じ作業ディレクトリを共有しているせいで `git status` がすぐにごちゃ混ぜになります。どの変更がどのタスクのものか判別できず、個別にコミットしたり戻したりするのも面倒になります。

2 つ目は、書き込み先の範囲が見えにくくなることです。ブランチを分けても、エージェントのプロセス自体は自分のユーザー権限のまま動いています。パスの解釈ミスや片付け用スクリプトが走った拍子に、リポジトリ外のファイルを書き換えてしまう可能性があります。とはいえ、ちょっとした修正のたびに Docker コンテナのイメージを用意して依存キャッシュをマウントするのは、普段の作業には重すぎます。

Ait がワークスペース作成時のディレクトリを 3 段階に分けているのは、この 2 つの悩みそれぞれに合わせるためです。

## ローカル、新しい Worktree、サンドボックス Worktree の使い分け

プロジェクト内にワークスペースを作成するとき、次の 3 つから選べます。

- **ローカル**：プロジェクトの既存チェックアウトをそのまま使います。1 つずつ順番に作業するときや、いま開いているブランチの続きを進めるのに向いています。
- **新しい Worktree**：Git worktree で独立したディレクトリとブランチを割り当てます。複数のエージェントが互いの変更や Git の状態を汚さずに並行作業できます。
- **サンドボックス Worktree**：Git worktree に加えて、エージェントプロセスに対して OS レベルの書き込み制限をかけ、許可されたパス以外への書き込みを抑えます。

通常の Worktree が解決するのはディレクトリとブランチの衝突だけで、プロセス権限は縛りません。書き込み先を制限するのはサンドボックス Worktree の役割です。この違いを押さえておくと、タスクごとに迷わず選べます。

## サンドボックス Worktree で守れる範囲と限界

対応する macOS / Linux ホストでは、現在 **Claude Code、Codex、Pi、Oh My Pi、OpenCode、MiniMax Code** でサンドボックス Worktree を利用できます。

仮想マシンの代わりと誤解しないよう、あらかじめ 2 つの境界を知っておく必要があります。

1. **主眼は書き込み制限であり、完全な読み取り隔離やネットワーク隔離ではない。** エージェントはモデル API へ通信する必要がありますし、ホストに導入済みのツールチェーンや読み取り専用の依存ライブラリも参照します。ネットワークや環境変数、ローカルの機密ファイルまで完全に遮断したい用途なら、専用の VM やコンテナを使うべきです。
2. **Linux ホストでは `bubblewrap >= 0.8.0` と非特権ユーザー名前空間が必要。** デスクトップ版を `.deb`、`.rpm`、あるいは Arch AUR の `ait-bin` で入れた場合はパッケージ依存として `bubblewrap` が入ります。AppImage、`tar.gz`、`ait-git` を使う場合は、`bubblewrap` を手動で導入し、非特権ユーザー名前空間が有効になっているか確認してください。

あえて Docker を必須にせず軽量な書き込み制限に留めているのは、普段の開発では「リポジトリ外を壊さないこと」を押さえつつ、ホスト側の Rust・Node・Python や手元のキャッシュをそのまま使いたい場面が多いからです。

## 並行作業が終わったあとの片付け

Worktree を作った直後は、プロジェクトの初期化スクリプトがバックグラウンドで走っていることがあります。最初にブランチを確認し、初期化が終わってからプロンプトを投げると、無用な依存エラーを避けられます。

並行して進めたタスクが揃ってきたら、ワークスペースの Git 操作でそのまま締められます。

- ワークスペースの主要アクションボタンは実際のブランチと PR の状態に合わせて、コミット・PR 作成・プッシュ・PR 表示へ切り替わります。GitHub / GitLab の操作には、作業ホスト側で `gh` や `glab` にログインしておく必要があります。
- v0.2.26 のクライアントと対応ホストであれば、グループ化された Git パネルで変更を整理して見られ、リモートに遅れたブランチも**リモートへのリベース**でそのまま追いつかせられます。
- マージ後は、実行中のエージェントや未回答の承認が残っていないか確認してからワークスペースメニューでアーカイブします。最初からやり直したい場合、条件を満たす管理対象の Worktree はリセットもできますが、確定前にブランチと消去されるファイルを必ず確認してください。

この流れに慣れると、3〜4 本の作業を同時に回していても手動で `git stash` を行き来する場面がほとんどなくなります。ディレクトリモードや Git 操作の詳細は [ワークスペース](/ja/docs/workspaces/)、Linux パッケージの依存関係は [対応プラットフォーム](/ja/docs/platforms/) をご覧ください。
