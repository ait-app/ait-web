コーディングエージェントと 2〜3 時間続けて作業していると、コードそのものより先に自分の頭が迷子になります。さっきの返信はどのブランチを変えたのか、ターミナルのエラーはどの編集に対するものなのか。途中で別のバグ修正に割り込まれると、どこまで検証したのかすら思い出せなくなりがちです。

Ait のワークスペースをうまく使うポイントは、こうした情報を同じタスクにまとめてくくりつけておくことです。

## 1 タスク 1 ワークスペース、名前はそのまま目的にする

プロジェクト内にワークスペースを作るときは、`test` や `tmp` のような数日後に思い出せない名前を避け、`fix-oauth-callback`、`mobile-nav-390px`、`docs-daemon-upgrade` のように作業内容をそのまま名前にします。

そのワークスペースには、エージェントの会話、プロジェクトファイル、ターミナル、Git の差分が並んで収まります。あとから戻ったときも、複数のターミナルタブで `git status` を叩き回る必要なく、どのブランチで何が変わっているかが一目でわかります。

## 依頼の時点で検証方法も一緒に書く

「トップページのナビゲーションを改善して」と頼むより、次のように範囲と確認手順を添えたほうがやり取りの往復が減ります。

> 幅 390px のモバイル画面でトップページのナビゲーションが開閉できるように調整してください。既存のスタイルは維持し、新しい依存パッケージは追加しないでください。変更後、ビルドコマンドを実行してエラーが出ないことを確認してください。

対象範囲・変えてほしくない点・確認コマンドを最初に伝えておくと、エージェントの推測が減り、差分レビューで見るべきポイントも絞れます。

## まとめを読む前に、差分と実行結果を見る

エージェントの完了報告はもっともらしい文章になりがちですが、無関係なファイルに触っていないか、境界ケースを落としていないかは、差分とコマンド出力で確認するしかありません。

- まず変更ファイルの一覧を見て、想定外のディレクトリに手が入っていないか確認する。
- ワークスペースのターミナルで、プロジェクト実際のテストやビルドを回す。
- 画面や CSS の変更があるときは、実際にプレビューを開いて崩れがないか目で見る。ビルドが通ってもレイアウトが崩れていることは普通にあります。

## 作業が分岐したら、同じディレクトリに詰め込まない

機能開発の途中で急ぎの修正が入ったり、実装案を 2 パターン比べたくなったりしたら、新しい Git worktree のワークスペースを切ってディレクトリとブランチを分けます。エージェントの書き込み範囲まで OS レベルで制限したい場合は、サンドボックス Worktree が使えます。違いは [1 つのリポジトリで複数のエージェントを同時に動かす：通常 Worktree とサンドボックス Worktree の違い](/ja/blog/sandboxed-worktrees/) でまとめています。

## 次のセッション向けに引き継ぎメモを残す

ひと区切りついて別のエージェントに引き継ぎたいときや、翌日に検証を持ち越すときは、2 つの機能が便利です。

- **ワークスペースのメモ帳**（実験的な機能から有効化）：Git のチェックアウト外にあるホストのデータディレクトリに、ワークスペース共有の Markdown を 1 つ保存します。「どこまで確認済みか」「まだ残っている問題」「次に回すコマンド」を書いておけば、デスクトップと Web から編集でき、権限のあるエージェントは Ait MCP 経由でそのまま読み書きできます。
- **タイムラインのエクスポート**：コンテキスト詳細から Markdown や HTML で出力できるので、作業ログを残したりチームに共有したりするときに役立ちます。

ディレクトリモードやメモ帳、セッション機能の詳細については、[ワークスペース](/ja/docs/workspaces/) と [エージェントセッション](/ja/docs/sessions/) をご覧ください。
